# Comment cleanup guide (C22)

Comments in `src/` should tell a reader what the code does and why it has to be that way. Most of the
current ones were written while porting: they name game.exe addresses, return sizes, vtable slots,
tickets and how the code used to be hooked. That history is in git; in the source it costs every reader
(and every model reading the file) tokens and attention. This guide says what stays, what goes, which
part a tool does, and how a batch is done and checked.

## What stays

- **What a function, class or member is for**, in a sentence, when the name does not already say it.
- **Why the code is written the way it is** when someone would otherwise "fix" it: the order of x87
  operations or a stored double that the goldens depend on, a draw of the game's `rand` that must happen
  even when the result is unused, iteration order that feeds game logic, a quirk of the original kept on
  purpose ("keeps the original's off-by-one: the last cell is never checked"), threading ("main thread
  only").
- **Byte layout that is still real**: save files, network packets, data read from game.exe's image until
  C18/C25 finish. Say that the layout is the file's or the packet's ("+0x10 in the save record").
- **Units and ranges** that the types do not say: half-cell units, degrees vs radians, 0..255 alpha.
- **Pointers to notes** (`docs/notes/ai.md`) once per file, in the file header, where the notes help.
- **Rebirth / our own changes**: a fix or option on top of the original says so briefly, with its flag
  ("Rebirth fix, EI_FIX_xxx: ...").
- **Tags tools read**: the rdata literal tags `0.5f /*0073B86C*/` (tools/rdata_literals.py) and every
  comment in a generated file (header "Generated by tools/..."). `tools/comments.py` never touches these.

## What goes

- **game.exe addresses** in comments, all of them. A function's address is in its registration
  (`EI_REWRITTEN(0x..., Name)`) while the registrations exist; nothing reads it from a comment. The same
  for data addresses: the named global is the reference.
- **Porting history**: "was a shim", "ported in S18i", "the hook era", "formerly", "now calls ...
  instead of ...", "(R16d)", "no longer a forwarder", "registered here because ...".
- **Ticket ids** (S18i, C11, R16d ...). A comment that needs a ticket names the open problem instead
  ("TODO: the client's list is still ordered by pointer"). Keep a ticket id only for open work, as
  `TODO(SV7b5): ...`.
- **Calling-convention and slot bookkeeping**: "(RET 4)", "slot 20", "__fastcall", "EAX 1", "+0x134"
  for a member that is now a named member, "the compiler's destructor", "inlined by the original"
  (unless the inlining changes behaviour the code keeps).
- **Restating the code**: "// the list destructor's body" over `list.RemoveAll();`, "returns true"
  over `return true;`, a comment that repeats the function's name in other words.
- **"As the original does"** with nothing after it. Either say what the constraint is ("x87 order:
  the goldens depend on it") or drop it.
- **Comment blocks that only list callers or callees.** The code shows them; a reader can grep.

## How a comment should read

- Present tense, about the code as it is: "Moves `target` to a cell the unit can stand on", not "This
  was 005BAC10; now it moves ...".
- Short. One line for most functions; a short paragraph only where the why is long.
- Names over numbers: the member, the function, the flag constant.
- Lines wrap at about 110 columns like the code (120 hard limit). When you shorten a comment block,
  re-wrap that block.
- Keep the file's own conventions (header comment at the top of the file, `// ---- Section ----`
  rulers) but drop section rulers that only group by ticket or address range.

Example, before:

```cpp
    // 006D8780 (RET 4): a random speech among those whose chance is at least `roll` (the game's
    // rand()); null, without drawing, when there is none. (The original also answers null for a
    // list whose first record has chance 0; S13.)
```

after:

```cpp
    // A random speech among those whose chance is at least `roll` (one draw of the game's rand());
    // null, without drawing, when there is none. Like the original, a list whose first record has
    // chance 0 answers null too.
```

## The mechanical part: tools/comments.py

- `python tools/comments.py stats [--files] [PATH...]` counts per area (or file): comment lines,
  addresses in comments, ticket ids, "the original" / "game.exe", history words.
- `python tools/comments.py apply [PATH...]` rewrites `//` comments in place by rule: a comment that is
  only addresses / ticket ids goes (its line too when it stands alone); an address header at the start
  ("006E3DC0 (RET 4). The name ...") goes; a parenthesis of only addresses / ticket ids goes; ticket
  ids at the edge of a parenthesis go. Run on all of `src/` once (C22's first commit: addresses
  19,415 -> 11,206, ticket ids 1,033 -> 539); run it again on a batch's files before the hand pass in
  case new comments arrived from other branches.
- `python tools/comments.py list [PATH...]` prints every comment line still holding an address or a
  ticket id: the to-do list of a batch.
- `python tools/comments.py samecode [REV]` fails when any file changed since REV differs in more than
  comments and whitespace. This is the batch's correctness check: with the code tokens unchanged, the
  build output is the same and no game run is needed.
- `python tools/comments.py check [--update]` is the ratchet: per file, addresses and ticket ids in
  comments may only go down (config/comment_baseline.csv). build.cmd runs it. Workers do not update the
  baseline (rows would conflict between branches); the coordinator runs `--update` after each merge.

## A batch (one Sonnet worker, medium effort)

A batch is a set of files (C22 child tickets name them by glob) of roughly 8,000 comment lines (user 2026-10-27).

1. Merge main. `python tools/work.py start <ID>`.
2. `python tools/comments.py apply <files>`, then `python tools/comments.py list <files>` and
   `stats --files <files>` for the to-do list.
3. Go file by file. Read the whole file, then rewrite its comments by this guide in one edit pass per
   file. Comments only: never change a code token, not even whitespace inside a line of code that has
   a trailing comment beyond removing the comment.
4. Every ~10 files: `python tools/comments.py samecode main` (0 files with more than comment
   changes) and commit. No build or game runs are needed while samecode is clean; build `release` once
   before the last commit (the build runs the ratchet).
5. Done when `list <files>` prints nothing (or only `TODO(ID)` lines for open tickets) and the history
   words count is near zero for the batch. `tickets.py set <ID> review`, report the before/after
   `stats` lines.

Don'ts: don't rename, move or reformat code; don't add new comments to code that has none unless the
code is unreadable without one (then one line); don't delete a comment that holds a real why only
because it mentions the original: rewrite it.
