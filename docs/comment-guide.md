# Comment cleanup guide (C22)

Comments in `src/` should tell a reader what the code does and why it has to be that way. Most of the
current ones were written while porting: they name game.exe addresses, return sizes, vtable slots,
tickets and how the code used to be hooked. That history is in git; in the source it costs every reader
(and every model reading the file) tokens and attention. This guide says what stays, what goes, which
part a tool does, and how a batch is done and checked.

## What stays

- **What a function, class or member is for**, in a sentence, when the name does not already say it.
- **Why the code is written the way it is** when someone would otherwise "fix" it: the order of x87
  operations or a stored double that the goldens depend on, a draw of the game's `rand` that must happen
  even when the result is unused, iteration order that feeds game logic, a quirk of the original kept on
  purpose ("keeps the original's off-by-one: the last cell is never checked"), threading ("main thread
  only").
- **Byte layout that is still real**: save files, network packets, data read from game.exe's image until
  C18/C25 finish. Say that the layout is the file's or the packet's ("+0x10 in the save record").
- **Units and ranges** that the types do not say: half-cell units, degrees vs radians, 0..255 alpha.
- **Pointers to notes** (`docs/notes/ai.md`) once per file, in the file header, where the notes help.
- **Rebirth / our own changes**: a fix or option on top of the original says so briefly, with its flag
  ("Rebirth fix, EI_FIX_xxx: ...").
- **Tags tools read**: the named-data tags right after an `=` (`kX[3] = /*0074111C*/ {1, 2, 3};`,
  tools/named_data.py) and every
  comment in a generated file (header "Generated by tools/..."). `tools/comments.py` never touches these.

## What goes

- **game.exe addresses** in comments, all of them. Nothing reads a function's address from a comment (no
  table keeps them since C20l: the port is the name). The same
  for data addresses: the named global is the reference.
- **Porting history**: "was a shim", "ported in S18i", "the hook era", "formerly", "now calls ...
  instead of ...", "(R16d)", "no longer a forwarder", "registered here because ...".
- **Ticket ids** (S18i, C11, R16d ...). A comment that needs a ticket names the open problem instead
  ("TODO: the client's list is still ordered by pointer"). Keep a ticket id only for open work, as
  `TODO(SV7b5): ...`.
- **Calling-convention and slot bookkeeping**: "(RET 4)", "slot 20", "__fastcall", "EAX 1", "+0x134"
  for a member that is now a named member, "the compiler's destructor", "inlined by the original"
  (unless the inlining changes behaviour the code keeps).
- **Restating the code**: "// the list destructor's body" over `list.RemoveAll();`, "returns true"
  over `return true;`, a comment that repeats the function's name in other words.
- **"As the original does"** with nothing after it. Either say what the constraint is ("x87 order:
  the goldens depend on it") or drop it.
- **Comment blocks that only list callers or callees.** The code shows them; a reader can grep.
- **Comments of deleted code.** Deleting a function, member, constant or declaration deletes the comment
  above it in the same edit; a comment that now describes nothing, or the next thing by accident, goes too.
  `comments.py check` counts the plainest case (a column-0 block followed by a namespace's `}`) as orphan
  comments, ratcheted at 0.

## How a comment should read

- Present tense, about the code as it is: "Moves `target` to a cell the unit can stand on", not "This
  was 005BAC10; now it moves ...".
- Short. One line for most functions; a short paragraph only where the why is long.
- Names over numbers: the member, the function, the flag constant.
- Lines wrap at about 110 columns like the code (120 hard limit). When you shorten a comment block,
  re-wrap that block.
- Keep the file's own conventions (header comment at the top of the file, `// ---- Section ----`
  rulers) but drop section rulers that only group by ticket or address range.

Example, before:

```cpp
    // 006D8780 (RET 4): a random speech among those whose chance is at least `roll` (the game's
    // rand()); null, without drawing, when there is none. (The original also answers null for a
    // list whose first record has chance 0; S13.)
```

after:

```cpp
    // A random speech among those whose chance is at least `roll` (one draw of the game's rand());
    // null, without drawing, when there is none. Like the original, a list whose first record has
    // chance 0 answers null too.
```

## The mechanical part: tools/comments.py

- `python tools/comments.py banned [PATH...]` lists the comment lines that hold a banned narration word (x87
  instruction names, stack slots, "as a dword", "the inlined ...", vtable slot numbers, and in src/game the MFC
  operation and class names of code that is std now); `check` fails when a file has more than its baseline (0).
  map_object_shadow.cpp keeps two until R26 rewrites it.
- `python tools/comments.py stats [--files] [PATH...]` counts per area (or file): comment lines,
  addresses in comments, ticket ids, "the original" / "game.exe", history words. With `--kinds`, the
  removal pass's candidate kinds instead (see "Removal pass", "Measuring").
- `python tools/comments.py apply [PATH...]` rewrites `//` comments in place by rule: a comment that is
  only addresses / ticket ids goes (its line too when it stands alone); an address header at the start
  ("006E3DC0 (RET 4). The name ...") goes; a parenthesis of only addresses / ticket ids goes; ticket
  ids at the edge of a parenthesis go. Run on all of `src/` once (C22's first commit: addresses
  19,415 -> 11,206, ticket ids 1,033 -> 539); run it again on a batch's files before the hand pass in
  case new comments arrived from other branches.
- `python tools/comments.py list [PATH...]` prints every comment line still holding an address or a
  ticket id: the to-do list of a batch.
- `python tools/comments.py samecode [REV]` fails when any file changed since REV differs in more than
  comments and whitespace. This is the batch's correctness check: with the code tokens unchanged, the
  build output is the same and no game run is needed.
- `python tools/comments.py check [--update]` is the ratchet: per file, addresses and ticket ids in
  comments may only go down (config/comment_baseline.csv). build.cmd runs it. Workers do not update the
  baseline (rows would conflict between branches); the coordinator runs `--update` after each merge.

## A batch (one Sonnet worker, medium effort)

A batch is a set of files (listed per ticket in config/comment_batches.txt; `--batch C22x` selects them) of roughly 8,000 comment lines (user 2026-10-27).

1. Merge main. `python tools/work.py start <ID>`.
2. `python tools/comments.py apply <files>`, then `python tools/comments.py list <files>` and
   `stats --files <files>` for the to-do list.
3. Go file by file. Read the whole file, then rewrite its comments by this guide in one edit pass per
   file. Comments only: never change a code token, not even whitespace inside a line of code that has
   a trailing comment beyond removing the comment.
4. Every ~10 files: `python tools/comments.py samecode main` (0 files with more than comment
   changes) and commit. No build or game runs are needed while samecode is clean; build `release` once
   before the last commit (the build runs the ratchet).
5. Done when `list <files>` prints nothing (or only `TODO(ID)` lines for open tickets) and the history
   words count is near zero for the batch. `tickets.py set <ID> review`, report the before/after
   `stats` lines.

Don'ts: no regex rewrites of your own across files beyond `comments.py apply` (scripts only to find
candidates): the C22a attempt cut "e.g. 00xxxxxx" to "(e.g.)", left "---: title ---", ";:", lone
trailing "// (file.cpp)" and "RET 4" / "ECX p" fragments. Read each file and rewrite its comments. Don't
rename, move or reformat code; don't add new comments to code that has none unless the
code is unreadable without one (then one line); don't delete a comment that holds a real why only
because it mentions the original: rewrite it.

## Removal pass

The passes above reworded comments; they removed few (47,951 -> 43,258 comment lines). The removal pass
deletes what a reader of the code does not need. Ask of each comment: does it tell something the
name, the types and the code beside it do not? If not, delete it; if partly, cut it to that part. A
declaration's comment says what the function is for and what a caller must know (a side effect, a
result that matters, units, a quirk); the steps belong to the body, which shows them. When in doubt
about a fact (a why, a quirk, a layout), keep it, shortened.

### What to delete

1. **Comments that restate the name or the code.** `// Stores the wind direction and strength.` over
   `void SetWind(const Vector3* direction, float strength);`, `// The fog start for `hour`.` over
   `float FogStart(float hour)`, `// Only on the server.` over `if (!world->IsServer()) return;`,
   `// CR LF` after `TrimRight("\r\n")`, a constructor's or destructor's comment that lists what its
   body assigns or calls, `// "ItemArmor"` after a `ClassName()` declaration.
2. **The same comment twice.** A function commented at its declaration and again at its definition
   keeps one: the header's for what it does, the definition's only for a why the body needs.
3. **Member-offset trailers and offsets in prose** (`// +0x1C ...`, "(CUnit +0x334)", "+0xCC").
   Drop the offset; keep the words after it when they say something the member name does not, and
   name members instead of offsets (`scale.z`, not `+0xCC`). Offsets stay only where the layout is
   still real: the code reads by offset (options.h's `field` constants), or the bytes leave the process
   or come from game.exe's data image (records read or written as raw bytes, network packets). Field
   and chunk ids of a file format stay (they are the format); `static_assert`s are code, not comments.
4. **Slot numbers.** `// 26` after a virtual, `// 9: LoadLever`, "Virtual slot 31 (...):",
   "Slots 11 / 12:". The virtual's name is the reference. They stay only where code still indexes a
   vtable or builds one by number (game_data.h's slot helpers) until those are converted.
5. **Registers and instructions.** "in ST0", "(EAX)", "AL = 1", "Callers test AL", "FCOMP + TEST
   AH,0x41: ...", "RET 4", "__fastcall", "(inlined)". Keep the behaviour they imply when the code does
   not show it ("a NaN counts as night"), without the instruction.
6. **Number trailers that repeat the literal.** `#define EI_TEN 10.0f /*0073CB98*/ // 10.0`,
   `return 220.0f; } // 220`. A trailer that decodes bits stays (`0x3D23D70A); // 0.04f`). The rdata
   literal tags `0.5f /*0073B86C*/` are gone (C41); the named-data tags after an `=` stay.
7. **File pointers.** `class ByteStream;   // core_streams.h`, "(lever_table_load.cpp)", "unit_lever.cpp:
   SetState, UseSpots; lever_object.cpp the rest". Grep finds them. The file header keeps its one
   pointer to docs/notes.
8. **Rulers** that are bare (`// -----`, `// --- ------`) or titled with the one function that follows
   (`// --- Close ---`). Rulers that name a group of functions in a long file stay.
9. **Stale claims from the hook era.** "Not rewritten", "through its address", "before the hooks are
   installed, so the hook never fires", "Rebirth patches it, so the vanilla launch only", "while it runs
   inside game.exe", "Names provisional", "a real virtual class: the compiler makes its vtable". All
   game code is ours and runs in the standalone image: say what is true now, or delete.
10. **"As the original" with nothing behind it**, and "like the original" after a statement that is
    plainly the behaviour. A quirk kept on purpose stays ("a count above 2 reads on into the record").
11. **Caller and callee lists**, sizes ("0x2C bytes") nothing depends on, "Returns this." where the
    type says it, and leftovers: a line that repeats the end of the line above, "// Small slots.", a
    callee list left in an empty namespace, a lone "(file.cpp)".

### What to move to docs/notes

A comment block of 8 lines or more (`long blocks`) that describes a subsystem, research or the
original's behaviour at large goes to the area's notes file (docs/notes/<area>.md) under a heading, and
the source keeps a one-line pointer ("See docs/notes/renderer.md, "Smooth option"."). Move, don't lose:
every fact lands in the notes or stays. What a reader of that one function needs stays at the function.

### What must stay

Everything in "What stays" above, in particular: why an x87 order, a stored double or a `rand()` draw
must stay; quirks of the original kept on purpose; save, packet and file layouts (field order, chunk
ids, offsets of raw records); units and ranges; Rebirth fixes and their flags; `TODO(ID)`; the rdata
tags; `} // namespace`. Trailers that give a member a meaning its name lacks stay, without the offset
(`float rate; // 1 / duration (0: no move)`).

### Re-wrap

Re-wrap every block you touch to about 110 columns; earlier passes left half-empty lines (`rewrap`
counts the lines a re-wrap saves).

### Measuring

`python tools/comments.py stats --kinds [--files] [PATH... | --batch ID]` counts, per area or file:

| column | what it counts |
| --- | --- |
| offset trailers | a comment after code that starts with `+0xNN` |
| offset mentions | other comments holding `+0xNN` |
| slot mentions | "slot N", "slots N", "vtable slot" |
| number trailers | a comment after code that is only a number (`// 26`, `// 0.8`, `// 10: empty`) |
| rulers | bare rulers and rulers titled with one word |
| registers | ST0, EAX..ESP, AL, RET n, calling conventions, "thunk", "inlined" |
| file trailers | `// file.h` after a forward declaration, `// "Name"` after a ClassName |
| stale claims | "not rewritten", "game.exe's code", "inside game.exe", "the hook build", "hooked" |
| bare original | a comment ending in "as / like the original (does)" |
| long blocks | lines in own-line comment blocks of 8 lines or more (docs/notes candidates) |
| rewrap | lines a re-wrap of the prose blocks at 110 columns saves |

The counts are candidates, not verdicts (a kept save layout still counts). A batch reports its files'
`stats --kinds` total before and after; it is done when the kinds are near zero except the kept ones
and the comment lines are down by about a third.

### A removal batch

As "A batch" above (merge, `work.py start`, file by file, the whole file read before its one edit pass,
comments only), with this section as the rules. Notes that long blocks move to go in the same commit as
their files. Check: `python tools/comments.py samecode main` clean (0 files with more than comment
changes) every ~10 files and at the end, `build.cmd release` once before the last commit, no game runs.
