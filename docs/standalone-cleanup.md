# What still ties the code to game.exe

Our code runs only in the standalone image, which contains no game.exe code; what is listed here is
left from when the code started inside game.exe, each item with the ticket that removes it (the plan
and order: `docs/cleanup-plan.md`; the counts: `python tools/progress.py`). Add an entry whenever a new
shim, stub or workaround lands.

## The address framework (C20, C29)

- Nothing of ours stands at game.exe's code addresses (C20 batch 6): no registrations, no code table. The
  image calls WinMain (`app::GameMain`) and everything else by name; no table maps game.exe's functions to ours
  (C20l). `src/hook/` and `include/ei/hook.h` keep game.exe's side (the vector recorders,
  `EI_RECORD`, which `InstallHooks` installs with EI_VECTORS=1) and the image's start-up actions.
- Our code calls game functions by name; src has no `EI_ORIGINAL` forwarders (C29). The harness changes
  the image's behaviour through named seams (the fixed ISAAC seed, the traced draws), not addresses; its
  patches of game.exe by address stay: that is the original's side.

## Data (C18, C18r, C18t, C25a, C18p)

- The data addresses left in code (`progress.py`'s "game data addresses"; `tools/data_seam.py` keeps raw ones out; 0 in src/ since
  C20u). They become named globals (`tools/named_data.py`). The build reads no game.exe (C25c): the image's data
  bytes are zero but the committed cells.
- The import table: `src/lib/gameapi.h` and `lib/import_table.h` (generated by `tools/gen_iat.py`); routed
  imports go through the image's slots (the harness's and the image's routes). C18p types them and
  shrinks the table to what is routed.

## Classes (C28)

- Hand-built tables: `ei::SetVtable`, slot calls by number and `__declspec(novtable)` classes whose constructors
  store a table. They become real virtual classes.
- `...Hook` / `__fastcall Fn(T* self, void*)` shims and `...Impl` slot bodies, which only existed
  because a pointer to a virtual member could not be registered.
- `offsetof` / `sizeof` asserts and `unused_XXX` padding (C36): kept only where bytes leave the process or come
  from a fixed format: save records written whole (UnitStats, UnitVitals, CameraView, WorldAlarm, ScriptBinding,
  TweenEntry, ScriptAreaPart, AnimationStep, the motion points), packets (net_messages.h, the order blocks,
  NetAddress, LockKey), resource files (map, sector, figure, mmp and res headers, the item and unit database
  records, the zone specs), external structs (D3D / DirectDraw / DirectInput / Miles / Bink, TLVertex), and the
  types the function vectors copy as bytes or read in game.exe's memory through our header (UnitParams,
  DamageInfo, IsaacRandom, LogicSettings, CoderState, the path cells). Some saves write a record by a literal
  size (`Read(&alarm, 16)`, `Read(views, 0xC0)`): grep `Read(&x, <number>)` as well as `sizeof` before
  dropping one. A literal-size memset can cover a pad after its member: Object3DClientSpecific's
  `memset(&sphere, 0, 0x38)` cleared the bounds and the 12 pad bytes after them, and zeroed `drawnRect` once the pad
  went (now `sizeof(sphere)`); grep `mem(set|cpy)(..., <number>)` near the class too. ParticleElement keeps its views' padding: the union's views alias each other's slots.
- Placeholder names: `Vector3::Construct`, `MappedFile::Construct` (original constructors written as
  methods returning `this` so they could be registered; real constructors), `using BOOL = int` (return
  values the original sets in all of EAX).

## Library code (C14a-d, C26)

- Strings, collections, files and archives are standard types and `src/lib`'s small classes (platform/file.h, gdi.h,
  thread.h, calendar.h, hash_map.h, intro_sort.h): no MFC or STLport class of ours is left (C14a-d).
- `libcrt::`: the host CRT, family by family, except where a golden proves the game's differs (C26;
  those go to C18r as our own CRT).

## Renderer

- The new renderer (`src/render`) reads the old Direct3D 7 device's state for every mesh pass (`render_mesh.cpp`, `ReadPassState`: the materials'
  state blocks are opaque) and reads textures and the interface windows' pixels out of the old DirectDraw surfaces (`render_textures.cpp`).
  Standalone: the materials from the game's data, textures from the .mmp files, the window surfaces as CPU buffers (or native drawing,
  `docs/notes/renderer.md` section 5). The window, cursor, cursor image and movie holders already work that way in the switch-over (`present` with
  `cpuwindows`, section 6): their pixels are only in the new renderer's memory (`render::SurfaceMemory`); outside it the same memory is still
  handed to DirectDraw as client memory, which goes with the old path.

## Behaviour the replacements must keep

- `gamecrt::tolower` / `strnicmp` use the game CRT's locale tables (Cyrillic archive names).
  A modern replacement must give identical results for bytes 0x80-0xFF.
- A hash map keyed by pointer values iterates in an order that depends on the pointers (the original's STLport
  `hash_map<void*, ...>`), so allocation order can change the order in which `MappedResource::FreeAllFiles` frees
  files. Harmless so far, but check before swapping allocators or containers (C14c).
- `lib::RoundEven` rounds to nearest, ties to even, as the original's FISTP; a C++ cast truncates.
- The game code is SSE2 (`/arch:SSE2 /fp:precise`, C30e15); the main thread still runs the x87 at 24-bit precision
  (device_object, as Direct3D set it): MSVC's x87 operations on values returned in ST0, the UCRT's log2 / exp2 / cbrt
  and Miles / Bink run under it (docs/notes/cleanup-tooling.md, "The control word").

## Original bugs kept on purpose

Decide case by case whether the fixes layer fixes them (docs/cleanup-plan.md, "Fixes layer").

- `MappedResource::CloseFile`: the write-failure message prints the data pointer as the file name.
- `MappedResource::GetFile`: leaks the data buffer when the read fails.
- `MappedResource::GetFile` on an in-memory archive does not report the size.
- `CTextureManager::LoadTexture` / `LoadTextureFrom`: leak the file buffer when the .mmp header is
  not recognised; the .bmp path reports format number 0 in its error message.
- `LinkFigureLoader::AddArchive`: leaks the archive object when opening fails; its log message
  passes the path string object by value to `%s`.
- `TweenArray::Load` reads the count into the slot of its stream argument (a stream that wrote
  nothing would leave the pointer value as the count).
- Effect objects and the sound file reader: see "Original bugs and oddities kept" in
  `docs/notes/effects.md` and `docs/notes/models.md` (a stopped sound is still moved, the ambient sound's count read into its
  argument slot, `_findfirst` handle leak, Seek origins).
- Delta replication, chunked files, clipper, network pump: see the "kept" lists in
  `docs/notes/network.md` and `docs/notes/core.md` (e.g. the 16-bit float packing's mantissa carry,
  `ReadQuad`'s order).
