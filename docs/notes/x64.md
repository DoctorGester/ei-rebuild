# x64: what a compile does not show

The data side of a 64-bit build: every file, save, network, resource and settings format the game reads or writes from
a value's or a struct's bytes, and every pointer or handle kept in a 32-bit field. The compile side (errors, the
layout asserts of the original, C4244 / C4267 / C4311 / C4312) is A3's note and A3a's work; the harness side is A3c's.

## Rules

- A value read or written as its bytes is a format value (`lib::kFormatValue`, src/lib/bytes.h): plain, no pointer, no
  integer wider than 32 bits. `ByteStream::ReadValue / WriteValue`, `platform::File::ReadValue / WriteValue`,
  `ChunkArchive::Field<T>` and the archive's `ValueAt` assert it. `std::ssize`, `size()`, `size_t` and `ptrdiff_t` are
  64-bit in an x64 build: a count goes in as `static_cast<std::int32_t>(...)` (none of the formats has a wider integer).
- A struct read or written whole has a `static_assert(sizeof(...) == n)` beside it (they all do now); a pointer, `long`,
  `size_t`, `time_t` or handle member does not belong in one.
- A read or write that spans several members (`Read(&panVelocity, 0x1C)`) holds only while no pointer member sits
  between them: 4-byte members stay packed the same in both builds. Never across a base class's end: a base with a
  vtable or a pointer is 8-byte aligned on x64, so its last 4-byte member may be followed by 4 bytes of padding before
  the derived class's first (the armour rows below; found by the combat golden on the x64 image, A3c).
- A pointer kept as an integer is `std::uintptr_t`, a handle the Windows type (`HANDLE`, `SOCKET`), never `std::uint32_t`.
- `long` / `unsigned long` are 32 bits on Win64 (LLP64) but 64 on Linux and macOS (LP64): none is in a format; the
  ones left (below) are Windows API mirrors that go with the platform layer.

## The x64 goldens (A3c)

How: `build.cmd verify-x64`, then `python tools/work.py test <ID> --x64 --golden --jobs 4` (and `--rebirth-only`); the
runs are in builderify-x64
uns (docs/notes/standalone.md, "The x64 build").

Against the goldens every run differs from the first spoken line on: without Miles a speaking unit never gets its
Blocked flag (0x800000, unit_client_models.h `talking`), so the hero's `#unit` hash differs and the 23 scenarios that wait
for `IsUnitBlocked(GetLeader())` time out. A 32-bit image built with Miles and Bink left out the same way (a scratch
change of image_imports.cpp LoadsHere, never committed) fails and differs exactly so: that is the Miles absence, not
x64, and the null audio backend (PL6) is to make both builds the same. So the proof is the x64 runs against that 32-bit
image's (console, every digest record and dump, the saves), 2026-10-30, vanilla 154 runs and Rebirth 32:
- the same: every scenario but the three below. No rounding difference showed anywhere (no x87 PC24 path on x64,
  C30e15): no pc24 helper or tolerance was needed.
- net_pair_master: the client lists no server (the second master's announcement through the sockets; A3d and PL5,
  merged after this branch started, rework them: run it again on current main, A3f).
- render_device_removed (record 4 only) and rebirth_flags (while the game is paused): the client unit's
  `animationStart`, which counts paused client ticks (unit_client_update.cpp RunTick), 33 and 11 apart; the server's
  state is the same. The same in each build run after run: open (A3f).
- Differences that did not repeat (each the same on a second run of both): the client unit's `animationStart` in the
  pairs (net_pair_join, net_pair_kick, net_pair_quest, net_pair_zone) and ui_gallery_deals, and the hero's animation after
  ui_widescreen_dialogue's timed-out wait: the real time between the games or after a failed wait.

Fixed on the way (the x64 image's bugs the runs found): the armour rows (above) and the client party's insert, which
moved 4 bytes per unit pointer (ui_battle_update.cpp; the second game of net_pair_zone crashed in HudPortraits::Rebuild
on a pointer cut to 32 bits).

## The probe (how the list was made)

A scratch x64 compile (never committed; A3a owns the real configuration): a copy of src, include and third_party under
build/, include/ei/x87.h's naked functions replaced by std:: calls, `_AMD64_` defined, the 32-bit-only layout asserts
commented out, crt_x87.cpp, device_object.cpp, world_client_shadow_casters.cpp, static_exit.cpp and the standalone
handlers left out; an object library of the rest built with vcvars64 and again with vcvars32 (about 70 s each).
Each serialisation template got `g_sink = &EiSizeProbe<T, sizeof(T)>::f;` before its copy, so every instantiation
leaves a symbol naming T and its size in the objects; `dumpbin /symbols` of both builds, compared, lists the types whose
size changes. (A deprecated-function warning does not work: MSVC reports one per source line.)
